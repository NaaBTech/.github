# Vendored GitHub Form Schemas

These JSON Schemas are used by `scripts/validate_docs.py` to check the organization's issue forms and vulnerability report form. They are committed to the repository so that validation is reproducible and does not depend on a network call.

## Files

| File | Applies to | Origin |
| --- | --- | --- |
| `github-issue-forms.json` | `.github/ISSUE_TEMPLATE/*.yml` | SchemaStore, modified — see below |
| `github-issue-config.json` | `.github/ISSUE_TEMPLATE/config.yml` | SchemaStore, unmodified |
| `github-vulnerability-report-form.json` | `.github/VULNERABILITY_REPORT.yml` | Derived in this repository from `github-issue-forms.json` — see below |

### A note on interpretation

The Apache-2.0 conditions above are applied here as a plain reading of the licence text and of the upstream NOTICE. Whether a particular distribution satisfies them in full is a question for the repository owners and their legal advisers; this document records what was done rather than certifying that it is legally sufficient.

GitHub does not publish a separate JSON Schema for private vulnerability reporting forms. The documentation states that these forms use the same YAML syntax as issue forms, and that they support the `checkboxes`, `dropdown`, `input`, `markdown`, and `textarea` elements — notably **not** `upload`. The vulnerability schema is therefore derived from the issue forms schema by restricting the permitted element types and the permitted top-level keys.

**`github-vulnerability-report-form.json` is a schema derived in this repository. It is not a schema published by GitHub, and it is not a SchemaStore schema.** Its `$id` points at its own path in this repository, not at a published URL. The restriction it encodes reflects GitHub's documented behaviour at the time of derivation; it is not a guarantee of what GitHub accepts at any later point.

Reference: <https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository>

## The one modification applied to the upstream schema

`github-issue-forms.json` is modified to add `min_length` to the `validations` block of the `input` and `textarea` elements.

**Why.** GitHub's form schema documentation lists `min_length` as a valid validation for `input` and `textarea` elements:

> `min_length` — Prevents form submission until the response contains at least the specified number of characters. Type: Integer. Valid values: A non-negative integer.

The upstream SchemaStore schema only lists `required`, so a form that uses a documented, valid GitHub feature would be rejected. The change adds `input_validations` and `textarea_validations` definitions and repoints the two element branches at them. The `dropdown` branch is left unchanged, because the documentation does not list `min_length` for it.

**What is not changed.** Every other part of the upstream schema is used exactly as published.

**The notice.** The modified file carries this key at its top level, as Apache-2.0 section 4(b) requires:

```json
"x-naabtech-modification": "Modified by NaaB Tech. Change: added the 'min_length' validation to the 'input' and 'textarea' elements, ..."
```

The full text is in `PROVENANCE.json`. The notice is added by `scripts/update_schemas.py`, so a future refresh cannot lose it.

## Maintenance procedure

The schemas are refreshed manually. CI never downloads them, so a schema host outage cannot fail a documentation change.

```bash
python scripts/update_schemas.py
```

The script:

1. Takes the update lock, so two refreshes cannot run at the same time.
2. Downloads both upstream schemas from SchemaStore, plus the upstream licence and NOTICE files.
3. Parses every download and checks that each schema is a valid JSON Schema.
4. Re-applies the `min_length` change and the Apache-2.0 section 4(b) modification notice to the issue forms schema, entirely in memory.
5. Regenerates `github-vulnerability-report-form.json` from the patched issue forms schema.
6. Builds the complete `PROVENANCE.json`, including every SHA-256.
7. Writes the whole artifact set into a temporary staging directory beside this one.
8. Verifies the staged files against the artifacts that were built, then promotes them into place.

### Recovery copies are kept per transaction

Every promotion gets its own directory below `schemas/.naabtech-backups/`:

```text
schemas/.naabtech-backups/
├── transaction-<unique-id-1>/
│   ├── github-issue-forms.json
│   └── third-party/
│       └── NOTICE-SchemaStore.txt
└── transaction-<unique-id-2>/
    └── ...
```

The identifier is unique and is never reused. A later transaction therefore **cannot** overwrite the recovery copy of an earlier one. Only the current transaction's directory is ever cleaned up; a directory from an earlier transaction, or one that still holds an un-restored backup, is left exactly as it is.

**The refresh is transactional against exceptions.** Nothing is written to the live schema directory until every download, patch, derivation and hash has succeeded and the staged files have been verified. If promotion fails part way through, the previous content of every file is restored and the original artifact set is left byte-for-byte unchanged. The staging directory is removed whether the refresh succeeds or fails.

**What that guarantee is, and what it is not.** The files are replaced one at a time, so the refresh is **not** a filesystem-level transaction. A crash or a power loss between two replacements can still leave a mixture of old and new schemas with stale provenance. What protects against that is the backup directory `schemas/.naabtech-backups/`: the original content of every file is kept there until the promotion has fully succeeded.

The rollback is itself failure-safe. If a backup cannot be restored, that backup is **not** deleted — it is the only remaining recoverable copy of that file — and its path is reported on standard error and in the raised error. The failed files are named, and the recoverable copies are left in one clearly identified transaction directory.

A successful promotion removes only its own transaction directory, and only the empty directories inside it, so a nested artifact path such as `third-party/NOTICE-SchemaStore.txt` leaves no empty child directory behind. A directory that still holds an un-restored backup is never removed, and every path that could not be removed is reported.

Concurrent refreshes are prevented by the lock file `schemas/.naabtech-update.lock`. If the file exists when a refresh starts, the refresh stops and says so. If no refresh is in progress and the file is stale, it can be removed by hand.

The staging, the promotion, the rollback, the per-transaction isolation and the concurrent-update guard are covered by failure-injection tests: a forced failure during promotion that proves every file is restored, a forced failure during restoration that proves the recoverable copy survives, a second failed transaction that proves the earlier recovery copy is byte-for-byte unchanged, a successful transaction that proves an earlier recovery copy is untouched, a refused concurrent refresh, and a successful nested promotion that proves nothing is left behind.

After refreshing:

```bash
python scripts/test_validate_docs.py
python scripts/validate_docs.py .
```

### Verifying the vendored files

The `vendored_sha256` values in `PROVENANCE.json` describe the bytes as they are committed, which are LF-terminated. `.gitattributes` normalises line endings to LF in every checkout, so the hashes can be reproduced from a fresh clone on any platform:

```bash
python - <<'PY'
import hashlib, json, os
d = "schemas"
p = json.load(open(os.path.join(d, "PROVENANCE.json"), encoding="utf-8"))
for name, meta in p["schemas"].items():
    with open(os.path.join(d, name), "rb") as handle:
        digest = hashlib.sha256(handle.read()).hexdigest()
    print(name, "MATCH" if digest == meta["vendored_sha256"] else "MISMATCH")
PY
```

### When to refresh

- When GitHub's form schema documentation changes.
- When a form in this repository is rejected by GitHub but accepted by the validator, or the reverse.
- As a routine check, a few times a year.

### When the change stops applying

`scripts/update_schemas.py` fails loudly if the upstream schema changes shape — for example, if the `form_item` definition no longer uses the `allOf` / `if` / `then` structure, or if the input and textarea branches can no longer be found. That is intentional: the change has to be reviewed against the new upstream schema rather than silently skipped.

## Coverage limitations

- The schemas describe the **structure** of a form. They do not describe whether the content is sensible, and they cannot detect a form that GitHub accepts but that is awkward for a reporter.
- `additionalProperties: false` in the upstream schema means unknown top-level keys and unknown attributes are rejected. If GitHub adds a new attribute, the upstream schema will need to catch up before this repository accepts it.
- The organization-specific rules that SchemaStore knows nothing about — the expected labels, the required file names, the internal links — are checked separately by `scripts/validate_docs.py`.
- `scripts/validate_docs.py` checks each vendored schema against the JSON Schema meta-schema for the dialect it declares, so a file that parses as JSON but is not a valid schema is rejected rather than used.
- The Apache-2.0 conditions are recorded here as a plain reading of the licence. Whether the distribution satisfies them in full is for the repository owners and their legal advisers to confirm.
