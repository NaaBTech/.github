# Vendored GitHub Form Schemas

These JSON Schemas are used by `scripts/validate_docs.py` to check the organization's issue forms and vulnerability report form. They are committed to the repository so that validation is reproducible and does not depend on a network call.

## Files

| File | Applies to | Origin |
| --- | --- | --- |
| `github-issue-forms.json` | `.github/ISSUE_TEMPLATE/*.yml` | SchemaStore, patched — see below |
| `github-issue-config.json` | `.github/ISSUE_TEMPLATE/config.yml` | SchemaStore, unpatched |
| `github-vulnerability-report-form.json` | `.github/VULNERABILITY_REPORT.yml` | Derived from `github-issue-forms.json` — see below |
| `PROVENANCE.json` | All of the above | Generated by `scripts/update_schemas.py` |

## Upstream sources

| Schema | Upstream URL | Reference documentation |
| --- | --- | --- |
| `github-issue-forms.json` | <https://www.schemastore.org/github-issue-forms.json> | <https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms> and <https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema> |
| `github-issue-config.json` | <https://www.schemastore.org/github-issue-config.json> | <https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository> |

GitHub does not publish a separate JSON Schema for private vulnerability reporting forms. The documentation states that these forms use the same YAML syntax as issue forms, and that they support the `checkboxes`, `dropdown`, `input`, `markdown`, and `textarea` elements — notably **not** `upload`. The vulnerability schema is therefore derived from the issue forms schema by restricting the permitted element types and the permitted top-level keys.

Reference: <https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository>

## The one patch applied to the upstream schema

`github-issue-forms.json` is patched to add `min_length` to the `validations` block of the `input` and `textarea` elements.

**Why.** GitHub's form schema documentation lists `min_length` as a valid validation for `input` and `textarea` elements:

> `min_length` — Prevents form submission until the response contains at least the specified number of characters. Type: Integer. Valid values: A non-negative integer.

The upstream SchemaStore schema only lists `required`, so a form that uses a documented, valid GitHub feature would be rejected. The patch adds `input_validations` and `textarea_validations` definitions and repoints the two element branches at them. The `dropdown` branch is left unchanged, because the documentation does not list `min_length` for it.

**What is not patched.** Everything else in the upstream schema is used exactly as published.

## Maintenance procedure

The schemas are refreshed manually. CI never downloads them, so a schema host outage cannot fail a documentation change.

```bash
python scripts/update_schemas.py
```

The script:

1. Downloads both upstream schemas from SchemaStore.
2. Re-applies the `min_length` patch to the issue forms schema.
3. Writes both schemas into this directory.
4. Regenerates `github-vulnerability-report-form.json` from the patched issue forms schema.
5. Rewrites `PROVENANCE.json` with the retrieval time and the SHA-256 of each upstream download and vendored file.

After refreshing:

```bash
python scripts/test_validate_docs.py
python scripts/validate_docs.py .
```

### When to refresh

- When GitHub's form schema documentation changes.
- When a form in this repository is rejected by GitHub but accepted by the validator, or the reverse.
- As a routine check, a few times a year.

### When the patch stops applying

`scripts/update_schemas.py` fails loudly if the upstream schema changes shape — for example, if the `form_item` definition no longer uses the `allOf` / `if` / `then` structure, or if the input and textarea branches can no longer be found. That is intentional: the patch has to be reviewed against the new upstream schema rather than silently skipped.

## Coverage limitations

- The schemas describe the **structure** of a form. They do not describe whether the content is sensible, and they cannot detect a form that GitHub accepts but that is awkward for a reporter.
- `additionalProperties: false` in the upstream schema means unknown top-level keys and unknown attributes are rejected. If GitHub adds a new attribute, the upstream schema will need to catch up before this repository accepts it.
- The organization-specific rules that SchemaStore knows nothing about — the expected labels, the required file names, the internal links — are checked separately by `scripts/validate_docs.py`.
